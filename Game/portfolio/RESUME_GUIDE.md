## (a) 프로젝트를 어떻게 설명할까

### a-1. 프로젝트 요약 템플릿 (이력서 1~2줄 / 자소서 첫 문단)

**한 줄 (이력서 프로젝트 칸)**
> 개인정보 무수집을 전제로 한 Unity 싱글 플레이 게임(달빛 모퉁이의 수인들)에서 **위협 모델링(STRIDE)·세이브 무결성 검증·비신뢰 입력 파서 방어·SBOM/출처 관리**를 설계하고, 자체 퍼징 하네스로 검증해 결함 8건을 찾아 전부 수정·회귀 시험 (`[기간]`, `[역할/기여]`)

**자소서용 도입 (4~5문장, 빈칸을 채워 쓰세요)**
> 저는 `[동기: 예) 개인정보가 처음부터 생기지 않게 설계하는 것이 가장 강한 보호라고 생각해서]` 게임 프로젝트를 정보보호 관점의 연습장으로 삼았습니다. 계정·분석·광고 없이 이름과 선택지만 로컬에 저장하는 구조를 정하고, 세이브 파일의 변조·손상·경로 조작·악성 입력 위협을 STRIDE 로 정리한 뒤 통제와 시험 방법을 짝지었습니다. 직접 만든 퍼징 하네스(고정 시드, 3만 5천여 회)를 돌려 세이브 로더는 크래시·무결성 우회가 없음을 확인했고, 스크립트 파서와 저장소 코드에서 **실제 결함 8건**(대부분 낮은 심각도)을 찾아 재현 방법을 정리하고 전부 수정해 회귀 시험을 붙였습니다. 이 과정에서 `[배운 점: 예) 통제가 있다는 주장보다 "어떻게 깨졌는지"를 재현하는 것이 설득력 있다는 점, 그리고 클라이언트 측 키의 한계를 숨기지 않고 문서화하는 태도]` 를 얻었습니다.

### a-2. 성과 bullet (STAR/성과 형식, 3~6개 중 골라 쓰기)

각 bullet 은 **상황(S) → 과제(T) → 행동(A) → 결과(R)** 를 한 줄로 압축한 형태입니다. 숫자는 모두 이 저장소에서 확인된 값입니다.

1. **위협 모델링과 설계 문서화**
   - S/T: 개인정보·세이브·스크립트·배포·의존성·AI 에셋 등 서로 다른 자산에 일관된 보안 기준이 없었음.
   - A: 자산·신뢰 경계·STRIDE 표(7개 영역)를 작성하고, 통제마다 **구현 위치·시험 방법·잔여 위험**을 대응시킨 설계 문서(`SECURITY_DESIGN.md`) 작성.
   - R: 통제 항목 `[N]`개를 파일 경로 단위로 추적 가능하게 정리, 한계(클라이언트 측 HMAC 키, 코드 서명 없음 등)를 문서에 명시. → *"무엇을 막고 무엇을 못 막는지"를 구분해 설명할 수 있게 됨*

2. **세이브 무결성·입력 검증 설계와 검증**
   - A: HMAC-SHA256 서명 + 상수 시간 비교, 서명 검증 뒤 범위 검증(`NaN/Infinity`·길이·리스트 크기), 임시 파일 교체 저장과 `.bak` 복구 구조를 분석·문서화·시험.
   - R: 변이 입력 6,000회에서 미처리 예외·hang 0건, 서명을 맞춘 범위 밖 위조 파일 **4,892건 전부 거부**. 단, 키가 클라이언트에 있어 의지 있는 변조는 막지 못한다는 한계를 **설계 문서에 명시**.

3. **퍼징 하네스 작성과 결함 보고**
   - S/T: 직접 구현한 대화 스크립트 파서와 세이브 로더가 비정상 입력에서 어떻게 동작하는지 근거가 없었음.
   - A: 고정 시드 변이 퍼저(`tools/security_selftest/`)를 작성해 잘림·바이트 변형·초장문·깊은 중첩·`../` 경로·`NaN` 등으로 시험, 재귀 깊이는 별도 프로세스로 격리.
   - R: **35,046 반복/케이스, 약 85초**. 세이브 로더 크래시·변조 수락 0건. 발견: 파일 저장소 폴더 이탈(`.tmp`), 숫자 오버플로 예외 계약 위반, 재귀 깊이·점프 순환 방어 부재, 이름 검증/저장 검증 불일치 등 **결함 8건(단언 실패 12개)** 을 심각도·재현과 함께 정리하고, **8건 모두 수정하고 회귀 단언을 추가, 재실행에서 단언 실패 12 → 0**(35,154 반복/케이스, 종료 코드 0).

4. **개인정보 최소화 설계와 문서 초안**
   - A: 처리 데이터 인벤토리(이름·성별 선택·종족·진행 정보), 수집·전송 경로 0건 확인 방법(grep), 개인정보 처리방침 초안, 기능 추가(계정·클라우드·분석) 시 달라지는 점과 PIA 체크리스트 작성.
   - R: "무수집"을 코드 검색으로 재현 가능한 형태로 문서화(네트워크 관련 API 사용 0건). 처리방침은 **법률 검토 전 초안**임을 문서에 표시.

5. **재현 가능한 검증 체계**
   - A: 순수 로직을 Unity 에서 분리해 7개 하네스(검사 **958**개)와 릴리스 점검 스크립트(시크릿 휴리스틱·SBOM 최신성 포함)로 자동 검증.
   - R: 하네스 전부 실패 0, 시나리오 전수 **1,595,664회 실행에서 오류 0**. Unity 측(NUnit 24개, 에디터 빌드)은 **미실행임을 문서에 명시**.

6. **공급망·출처 관리 설계**
   - A: CycloneDX SBOM 생성기·최신성 검사, 서드파티 고지 초안, AI 에셋 출처 기록 양식(도구·모델·약관 확인일·`ai_assisted`).
   - R: 구성 요소 10개를 기계 판독 형식으로 기록(버전 미확정 4개는 표기). 출처 기록은 **양식 단계(기록 0건)** 임을 명시.

> - 수동 보안 리뷰(`docs/19_Security_Review.md`, 발견 13건)는 **누가 수행했는지 본인 사실대로** 적으세요. 그중 8건을 수정했고 N-6(부분)·N-9·N-11·N-12 는 미해결, N-13 은 설계상 수용입니다(`[본인 역할]`).

> **쓰지 말아야 할 표현**: "보안 인증 획득", "취약점 N건 제보/CVE", "실제 사용자 N명", "침해 사고 대응", "ISMS-P 준수", "변조 방지 구현"(→ "변조 **탐지**"), "상용 수준". 이 저장소에는 그런 근거가 없습니다.

## (c) 면접 질문과 모범 답변 (이 저장소 기준)

> 답변은 그대로 외우지 말고 **본인 말로** 바꾸세요. 모르는 것을 아는 척하지 말고 "확인하지 못했다 / 이렇게 확인하겠다"로 말하는 것이 오히려 신뢰를 줍니다.

**Q1. 로컬 세이브에 왜 HMAC 을 썼나요? 의미가 있나요?**
> 목적을 두 가지로 한정했습니다. 첫째 전원 차단·디스크 오류 같은 **우발적 손상 탐지**, 둘째 메모장으로 숫자를 고치는 수준의 **단순 편집 탐지**입니다. 서명이 맞지 않으면 `Tampered` 로 구분하고 `.bak` 으로 복구합니다. 다만 HMAC 키가 클라이언트(소스)에 있어서 키를 아는 사람은 유효한 서명을 만들 수 있으므로 **의지 있는 변조는 막지 못한다**고 코드 주석과 설계 문서에 적었습니다. 싱글 플레이 게임이라 강한 DRM 은 의도하지 않았고, 그래서 서명보다 서명 뒤에 오는 **범위 검증**(`SaveValidator`)을 실제 방어선으로 보고 시험했습니다. (`SaveIntegrity.cs`, `SECURITY_DESIGN.md` §10)

**Q2. 키가 소스에 있으면 의미 없는 것 아닌가요? 어떻게 개선하겠습니까?**
> 기밀성이 필요한 데이터가 아니므로 로컬 서명은 "탐지" 용도로만 유지하는 것이 합리적이라고 봅니다. 변조 방지가 실제 요구사항이 되면(예: 랭킹·결제 연동) **서버가 검증하는 구조**로 바꿔야 하고, 그때 클라이언트 측 키는 신뢰하지 않습니다. 로컬만 한다면 하드웨어 보안 저장소(플랫폼 키스토어)를 쓸 수 있지만 루팅/메모리 조작에는 여전히 한계가 있습니다. 중요한 건 한계를 알고 위협 모델에 맞는 수준을 고르는 것이라고 생각합니다.

**Q3. 클라우드 저장이나 분석(애널리틱스)을 추가한다면 무엇이 달라지나요?**
> 전제가 "무수집"이므로 거의 모든 것이 달라집니다. 데이터 인벤토리와 처리방침 개정, 수집 목적·보유기간 정의, 동의/옵트인 UI, 전송 구간 TLS·저장 암호화, **서버 측 검증**(클라이언트 HMAC 에 의존 금지), 계정이 생기면 인증·접근통제·로그, 이용자 권리 행사(열람·삭제) API, 국외 서버라면 국외 이전 요건 검토, 침해 사고 대응 절차, PIA 재수행이 필요합니다. 설계 문서 §8.5 표와 §8.6 체크리스트로 정리해 두었고, 실제 법적 요건은 최신 법령과 전문가 확인이 필요하다고 명시했습니다.

**Q4. AI 가 만든 에셋의 출처(provenance)는 어떻게 관리하나요?**
> 설계는 있고 기록은 아직 비어 있다고 먼저 말씀드리겠습니다. `docs/legal/art_log.csv` 양식에 에셋 ID·생성 일시·도구와 버전·모델/LoRA 이름·라이선스 근거와 **약관을 확인한 날짜·URL**·프롬프트·시드·`ai_assisted` 여부를 한 장당 한 줄로 남기게 했고, 점검표에는 학습 데이터에 타인 저작물을 쓰지 않는 것, 실존 작가 이름을 프롬프트에 쓰지 않는 것, 스토어의 AI 공개 설문에 이 기록으로 사실대로 답하는 것을 넣었습니다. 일러스트가 제작되면 그때부터 기록을 채우는 것이 다음 단계입니다. `[실제 제작 현황을 사실대로]`

**Q5. 개인정보 보호법(PIPA) 기본 개념을 설명해 보세요.**
> `[본인이 공부한 내용으로]` 개인정보는 살아 있는 개인을 알아볼 수 있는 정보(다른 정보와 쉽게 결합해 알아볼 수 있는 것 포함)이고, 처리자는 수집 시 목적을 정하고 **최소한**만 수집하며, 정보주체의 동의 등 적법 근거가 필요하고, 목적 달성 후 파기해야 하며, 안전성 확보 조치와 처리방침 공개 의무가 있다고 이해하고 있습니다. 민감정보·고유식별정보는 더 엄격하고, 아동(법정 연령 기준은 최신 조문 확인 필요)은 법정대리인 동의 같은 가중 요건이 있습니다. 제 프로젝트에서는 수집이 없어서 이 의무들이 거의 적용되지 않는다고 **설계상 판단**했지만 법적 결론은 전문가 확인이 필요하다고 문서에 적었습니다. (세부 조문·수치는 면접에서 단정하지 말고 "법령을 확인하겠다"로.)

**Q6. 이 게임이 가진 개인정보는 무엇이고 어떻게 최소화했나요?**
> 주인공 이름, 성별 선택, 종족 선택, 외형 프리셋, 진행 정보뿐이고 전부 기기 로컬에만 저장됩니다. 계정·기기 식별자·IP·위치는 없습니다. 성별은 "지정 안 함"과 논바이너리를 기본 선택지로 둬서 **민감할 수 있는 선택을 강제하지 않았고**, 이름은 길이·제어문자 검증을 거칩니다. 네트워크 관련 API 사용이 0건임을 grep 으로 확인하는 방법을 문서에 남겼습니다. 다만 빌드된 앱의 실제 권한 목록은 아직 확인하지 못했습니다.

**Q7. 슬롯 이름을 통한 경로 조작은 어떻게 막았고, 퍼징에서 무엇이 나왔나요?**
> 슬롯은 정수만 받아 `slot0~3.json` 이름을 만들기 때문에(범위 밖은 예외) 앱 경로에서는 사용자 문자열이 파일명에 들어가지 않습니다. 저장소 계층도 `Path.GetFileName` 으로 한 번 더 방어합니다. 이를 시험하려고 저장소에 직접 `../x`, 절대 경로, `..\`, 널 문자 등 3,031개 이름을 넣었는데, 외부 파일을 읽거나 덮어쓴 경우는 0건이었지만 **빈 이름이나 `/` 로 끝나는 이름에서 저장 폴더 바깥에 `.tmp` 파일이 생기는 결함**을 찾았습니다. 앱 경로로는 도달 불가라 Low 로 분류했고, 이름 검증을 `PathOf` 에서 예외로 처리하는 패치안을 적었습니다. (`SELFTEST_RESULTS.md` F-1)

**Q8. 파서를 "비신뢰 입력 파서"로 본 이유와 결과는?**
> 시나리오는 번들이라 신뢰할 수 있지만, 작성 실수나 앞으로의 현지화·모드 파일 도입을 생각해 외부 입력처럼 다뤘습니다. 언어를 닫힌 문법으로 만들어 임의 코드 실행 경로를 없앴고, 모든 구문 오류가 줄 번호가 붙은 예외로 나오게 했습니다. 변이 퍼징 3,000회에서 문서화된 예외 외에는 없었지만, 표적 시험에서 **거대 숫자 → 예외 종류 위반, 재귀 깊이 무제한, 점프 순환 무한 루프, 한 줄에 태그 2만 개 → 약 2.9초(이차 시간)** 를 찾았습니다. 번들 콘텐츠에서는 도달하지 않아 Low 로 매겼지만 외부 스크립트를 받는다면 우선순위가 올라간다고 정리했습니다.

**Q9. 서명 검증과 범위 검증의 순서·역할은?**
> 로드 순서는 파싱(예외는 `Corrupt`) → 서명 재계산·상수 시간 비교(`Tampered`) → 범위 검증(`Corrupt`)입니다. 서명은 우발적 손상과 단순 편집을 먼저 거릅니다. 하지만 키가 공개된 것이나 마찬가지라 서명을 맞춘 위조 파일은 통과할 수 있으므로, 그다음 범위 검증이 상태에 들어가는 값을 제한합니다. 퍼징으로 서명을 맞춘 범위 밖 파일 4,892건이 모두 거부됨을 확인했고, 반대로 `SatisfactionBonus` 나 캐릭터 ID 같은 **검증하지 않는 필드**가 있음도 찾아 F-7 로 기록했습니다.

**Q10. 발견한 결함 중 무엇을 가장 먼저 고치겠습니까? 기준은?**
> 영향 × 도달 가능성으로 매겼습니다. (1) F-6 이름 검증/저장 검증 불일치는 일반 플레이어가 겪을 수 있는 기능 결함이라 먼저 고칩니다(한 줄 패치). (2) F-4 점프 순환 무한 루프는 콘텐츠 실수 한 번으로 게임이 멈추므로 실행 스텝 상한과 린트를 추가합니다. (3) F-2 숫자 오버플로·F-3 재귀 깊이는 파서 예외 계약을 지키는 작은 수정입니다. (4) F-1 저장소 경로 이탈은 현재 도달 불가지만 방어 심층으로 수정합니다. 수정 후에는 자가 테스트를 회귀 테스트로 릴리스 점검에 넣어 종료 코드 0 을 확인할 계획입니다.

**Q11. (추가) 아동이나 연령은 어떻게 고려했나요?**
> 콘텐츠는 성인 캐릭터와 암시적 표현으로 제한했고 대상 연령은 아직 정하지 않았습니다(처리방침 초안의 `[TODO]`). 개인정보 관점에서는 계정·수집이 없어 아동 개인정보 수집 문제가 생기지 않는다고 설계상 판단했지만, 연령 등급은 배포 플랫폼 절차를 따라야 하고 온라인 기능을 추가하면 아동 요건을 다시 검토해야 합니다.

**Q12. (추가) 이 프로젝트의 가장 큰 한계는?**
> 클라이언트 측 HMAC 키, 코드 서명 부재, 지속적 퍼징 부재, 그리고 Unity 에디터에서 실행하지 못한 부분(JsonUtility 동작·에디터 빌드 스크립트·NUnit 24개)입니다. 퍼저도 단순 변이 방식이라 "충분히 검증했다"고 주장하지 않습니다. 한계와 로드맵은 `SECURITY_DESIGN.md` §10 에 있습니다.
